# P2.1 / P2.2 预约跟进交付记录

日期：2026-09-15。范围为仓库实现及本地隔离验收，不代表持久环境迁移或发布通过。

## 已实现的流程

管理员工作台增加第八项“预约跟进”，汇总店休待联系与过期待跟进数量。列表采用两行双列筛选，支持两类事项各自的待处理与已完成记录；点击预约进入原详情，在联系方式后填写跟进结果与说明。

| 类型 | 进入待处理条件 | 继续提醒 | 完成条件 |
|---|---|---|---|
| 店休联系 | 单日或固定店休导致预约取消，且没有完成跟进 | 待重试、号码不可用 | 实际联系后保存“已联系”，或说明原因后“结束跟进” |
| 过期跟进 | 服务端时间达到预约开始时间，预约仍为 pending，且没有完成跟进 | 待重试、号码不可用 | 核实后保存“结束跟进” |

每次保存必须填写 1–500 字说明。记录包括处理结果、说明、管理员 ID、时间和版本；历史只追加，不提供改写、删除或重新打开。拨号、阅读详情、顾客已读及微信通知均不自动结束跟进。没有独立的定时重试任务，后续联系安排由员工写入说明并在待处理队列跟进。

已有店休取消和过期未确认预约会按相同规则直接进入队列；不写入虚构联系记录或批量改变预约状态。首次启用时，门店需核对历史上已实际联系的事项并补记处理结果。过期跟进结束后，原预约仍显示过期提示；原 P1 过期记录列表保留历史，本次新队列单独维护是否完成跟进。

## 安全、事务与接口检查

- 新路由仅 ADMIN+ 可读写，普通顾客及禁用账号不可访问内部记录；参数、结果、分页及服务端返回数据均校验。
- API → Service → Repository → Model 分层；没有业务 Service 互调，读取不创建任务，列表批量取最近记录，避免逐条查询。
- 写入在事务内先锁预约，再做 MySQL 当前读；版本不一致、完成后追加、无效类别结果及不符合条件均返回明确冲突。
- 相同请求键、管理员及精确内容重放不会重复写入；不同管理员竞争同一版本，仅一方成功。未知保存结果锁定原草稿并重试同一请求，避免重复联系及重复记录。
- 新表仅增加跟进事实，不修改预约、订单、资金或顾客提醒已读状态。唯一索引保护版本和请求键，两个外键使用 RESTRICT，完成查询使用对应索引。
- 已同步需求、API/OpenAPI、数据库设计/DBML、迁移流程、架构、前端契约、产品/设计记录及 changelog。

## 2026-09-15 · 微信说明输入问题修正

用户反馈预约详情说明框无法输入。跟进 Textarea 改为明确传递布尔 disabled，避免将按钮为 H5 省略 false 属性的处理套用于原生输入控件；输入事件在锁定时不改写草稿。新增读取失败保护已有草稿、恢复后继续编辑和保存的测试，相关 7 项测试、TypeScript、定向 ESLint 通过。既有微信监听器已生成更新产物。

开发者工具当前预约 #15 中，通过原生控件设置输入值后，保存按钮可用；清空后按钮禁用。验证文字已清除，没有提交跟进记录。随后用户确认下述 5 项手工测试全部正确，说明填写与保存流程的用户复测已通过；不将此结论外推为手机真机键盘验收。
