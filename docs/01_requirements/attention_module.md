# 站内提醒 P1.1–P1.3：预约、订单、桌台与资金结果

> 2026-09-14；仓库实现与隔离验证完成，目标环境未迁移、未发布。
> 本文为已实现规则；跨模块后续范围见 [整体规划](home_attention_notification_plan.md)。

## 范围与计数

第一步覆盖预约审核、确认/拒绝结果、单日与固定店休取消、顾客取消已确认预约，以及预约开始后仍未受理的提示。P1.2 已扩展订单与桌台交接（见下文）；资金结果已按 P1.3 接入；微信投递尚未接入。原预约状态机、取消期限、人工电话联系及权限规则保持适用。

| 接收方 | 提醒条件 | 消除条件 |
|---|---|---|
| ADMIN+ | `pending` 且服务端当前时间严格早于开始时间 | 确认、拒绝、取消成功，或到达开始时间；查看不消除 |
| 顾客本人 | 门店确认、拒绝、店休取消产生未读结果 | 详情成功展示对应预约版本后，确认该次展示的明确事件 ID |
| 门店共享 | 顾客取消一条已确认预约 | 任一 ADMIN+ 在详情点击“已知悉”；记录首次知悉人和时间 |
| ADMIN+ 过时视图 | `pending` 且当前时间大于或等于开始时间 | 独立展示，不计首页可处理红圈，也不新增预约业务状态 |

顾客取消待确认预约仅消除门店审核待办，不额外生成取消变更。顾客自己的取消操作不生成本人未读。恢复营业不恢复历史预约，也不产生恢复通知。

按预约去重：同一预约先确认、后店休取消且均未读，只计 1；两条预约计 2。管理首页总数为可审核预约数加共享未读预约数；当前两者分别为 pending 和已取消预约，集合互斥。过时数量单列。顾客汇总只返回本人未读，可处理和过时计数为 0。

## 入口与阅读

管理员首页“待处理／预约审核”显示红圈及“待审核 N · 取消变更 M”。进入预约待办页后可切换待审核、取消变更、已过期，并可打开完整预约列表。顾客商城首页和预约页显示“我的预约”结果入口，预约 Tab 镜像同一数量。无新结果时不显示结果入口；0 隐藏，1–99 显示数字，超过显示 99+，列表保留真实总数。

列表、首页、预加载和读取接口不标记已读。详情先显示权威预约业务内容，再请求包含 `reservation_updated_at` 的提醒快照；仅版本一致、当前身份一致且页面前台可见时，顾客提交确切事件 ID。版本不一致时刷新详情。服务端只确认本接收方事件，混入不存在或其他接收方事件时整批失败，不接受“把最新全部已读”。新到事件不会被旧详情的确认误清。管理员共享变更必须显式点击“已知悉”。

业务变化和结果事件在同一事务提交，任何一方失败都整体回滚。同一业务转态用唯一事件键防重。结果事件不可覆盖，阅读更新幂等且保留首次阅读人/时间。站内已读不能证明已经电话联系，也不能证明微信送达。

## 刷新、失败与身份

显示相关页面时立即获取服务端汇总，管理员约 10 秒、顾客约 30 秒刷新；汇总请求失败后改为约 60 秒重试。页面隐藏或卸载时停止对应轮询。业务处理成功、阅读确认成功及回到页面时刷新，进入其他顾客根 Tab 时也同步汇总；同一身份在途汇总请求合并。

首次请求失败明确显示暂不可用；后续失败保留旧数量并提示刷新失败，不用 0 冒充空待办。读取或已读写入失败不阻止查看业务详情，保留重试入口。退出或账号/角色变化时清空内存提醒，忽略旧身份迟到响应；服务端仍独立验证身份、角色与归属。

## 存储、上线与后续

P1.1 每个结果只有一个接收目标，采用一张 `attention_events` 表；非空 `user_id` 为顾客本人，空值为门店共享。没有预建微信收件地址、订阅、投递或通知 Worker。字段及索引见 [数据库设计](../02_database/database_design.md)，协议见 [提醒 API](../03_api/attention_api.md)。

M12 为追加建表迁移。既有仍可审核预约自动参与实时统计；上线前历史确认/拒绝/取消不回填未读，避免历史红点集中出现。切换后新业务结果才写事件。目标环境迁移与启用须遵循发布授权和迁移流程；已存在事件时迁移拒绝降级删表。

订单与桌台已按下述 P1.2 接入，首版提醒所有仍在付款时限内的待付款桌台，不增加顾客“我已付款”步骤。P1.3 资金结果已接入，下一步 P1.4 联合验收；微信阶段另行核验平台能力及订阅条件。

## 2026-09-14：待办页面精修与过期展示统一

预约待办页复用既有管理页的 Ribbon Ledger 页头、真实纹理资产、圆角筛选面板、胶囊选项和预约卡片；空状态提供下一步入口。初次进入时依次优先显示待审核、取消变更、已过期中首个非空集合，之后尊重用户选择，不因轮询重置选项。

管理完整列表新增“已过期”筛选；“待确认”明确请求尚未开始的 pending，“已过期”请求开始时间小于或等于服务端当前时间的 pending。筛选在服务端分页前完成，总数与记录一致；旧客户端省略 review_timing 时保持历史 pending 查询语义。持久化状态仍为 pending，不能伪造已拒绝/已取消。

管理与顾客预约列表、详情统一派生“已过期未处理”标签和联系门店提示。展示时钟仅在前台运行，管理审核入口在过期后收起；操作权限与时间边界仍由服务端最终复验。此修订无新数据库迁移、依赖或版本号调整。视觉与操作证据见 [设计检查](../08_frontend/qa/attention-refinement-review.md)。

## P1.2：订单与桌台交接（2026-09-14）

本节扩展 P1.1，覆盖普通待付款、有效占台待付款、订单履约、人工/余额付款结果、订单完成及独立桌台结束。代客订单、调账和退款结果已按下文 P1.3 接入。微信仍延期。

- 待付款桌台：`awaiting_payment`、关联订单仍 pending，且服务端当前时间小于或等于付款截止时间。与可信付款边界一致，严格超过才失效；按会话计 1，不按 Timer 计。直接开台没有顾客账号，不产生顾客提醒。
- 普通订单待付款：pending，排除上述有效占台订单。同一占台不会同时增加订单与桌台首页数字。过期只释放桌台，不取消原订单，原订单重新进入普通待付款。
- 管理员待履约：paid 且无 pending/succeeded Refund；存在尚未结束的 active 桌台时标“服务中”，其余为“待履约”。收款成功后桌台待付款消除、订单履约新增；完成后履约消除。
- 顾客订单入口：普通待付款与未读订单结果的并集；顾客桌台入口：有效待付款会话与独立未读结束会话的并集。查看结果不会完成付款待办。
- 人工收款与余额付款各自按首次成功付款写一件订单结果，完整摘要含付款方式、金额及是否开始桌台计时。钱包重放不再写新结果。付款时原占台已经超时，结果明确“未启动计时”并关联旧会话。
- 订单完成写一件订单结果，关联的桌台结束不另计一件。付款/完成业务路径引起的关闭统一合并；独立付款超时、体验及缓冲到期、管理员释放才写以精确会话为主事项的结束结果。预约事件继续按预约聚合。

事件和业务/资金变化在原有事务内共同成功或回滚，追加事件写入位于既有业务锁之后。重复付款、释放和时间收敛依赖原锁、状态机及唯一事件键，不另建抢单、收款申请或支付状态。

顾客商城首页显示订单/桌台事项，会员中心订单提醒按事项显示，但“我的桌台”为固定业务入口，不随待办或未读归零而隐藏。会员 Tab 仍只镜像两类提醒总数，不把正常使用中或已读历史记录算作待办。预约页只显示预约提醒。管理员订单入口进入订单待办，桌台存在待付款时进入对应会话列表，列表均可返回完整业务入口。新筛选最多三项直接显示；无横向滑轨。

顾客订单详情和桌台页面先渲染每条不可变结果摘要，再提交当前账号实际展示的确切事件 ID；成功后保留结果内容。结果已读和业务当前状态独立，旧收款结果不会因为后来完成而被隐藏。付款/完成新结果到达订单详情时同步重新读取订单与资金，避免旧操作状态滞留。失败可重试；隐藏/卸载/身份变化不接受旧响应。

新增 owner-only 精确历史会话接口与“本次桌台”页；始终以 session_no 查询，即使该桌已有新顾客或同一人重开，也不会跳到新会话、误清新事项。关联订单仍可查看和付款。桌台结果复用其页面刷新节奏，不叠加独立结果轮询；订单结果前台约 30 秒检查，隐藏时停止。已关闭历史会话停止业务轮询。

M13 增量扩展 `attention_events` 的订单、会话关联和安全结果摘要，不补历史未读；存量真实待办立即计入。数据库、HTTP 契约与隔离检查分别见对应文档。新客户端需新汇总字段；旧客户端仍可使用原业务接口，但不会自动确认这些结果。目标环境须先迁移，再启用代码；本地持久 SQLite 不能靠 generate_schemas 自动升级，须按独立授权的升级流程处理。

## 会员固定桌台入口修复（2026-09-14）

会员中心“我的桌台”在普通顾客登录后固定展示，首次汇总尚未返回或失败时也能进入；无提醒时仅隐藏数字角标。点击后默认查看本人的全部开台记录，按创建时间与 ID 降序稳定分页，包含待付款、使用中及已结束会话；付款成功、结果已读均不移除记录。待付款／新结果筛选继续使用原提醒集合。每条记录仍以 session_no 进入精确详情，避免同一桌台重开后误跳到别人的会话。无记录时显示“还没有开台记录”。

完整桌台记录使用独立只读查询，原提醒 all、汇总、管理员待付款队列及已读规则保持兼容。列表查询不创建提醒、不标已读；进行中的会话不产生额外红圈。状态标签按付款截止和桌台释放绝对时间派生，不依赖后台任务及时收敛。无新增持久字段、迁移或历史数据回填。


## P1.3：资金结果（2026-09-14）

- 管理员代客钱包下单在原事务成功后产生一条订单结果，显示扣款金额及当时余额；不额外产生普通钱包支付通知，也不复制内部订单备注。幂等重放沿用原结果。
- 全额钱包退款产生“退款已退回余额”；人工退款产生“门店已登记线下退款”，明确线下到账需与门店核实。退款、钱包入账及本次桌台结束合并为订单事项，保留精确会话链接。原订单状态仍可能为 paid/completed，履约队列继续排除 pending/succeeded Refund。
- 管理员余额调整按每笔不可变流水产生一件结果，增加与减少分开记录。顾客首页/会员中心“余额变动”显示未读数量，会员 Tab 合并订单、桌台与独立调账数量。代客扣款和退款只在订单入口计数。
- 余额列表支持“新结果”和“全部调整”，列表不标已读；精确详情完整展示正负金额、调整前后余额、原始流水编号、发生时间及顾客资金明细中已经可见的调账原因，再确认该事件。标明余额为本笔发生时余额，不能冒充当前余额。已读详情仍可复看，资金明细页保留结果列表入口。
- 256 字调账原因从原始流水读取，不截断或复制到 255 字结果摘要。返回字段不含操作者信息、幂等键、内部备注或个人联系方式。查询同时验证事件接收者与原始流水钱包归属，任一不符均不可访问。
- 同一次资金事务写入结果事件，任一步失败全部回滚；重试不重复记账或新增提醒。被禁用顾客允许现有合法纠错/退款产生结果，但仍受原认证限制。
- 仅新业务成功事件生成提醒，不回填历史已完成资金结果。复用 M13 结构及唯一事件键，见数据库与架构说明；无新持久迁移。微信通知继续延期。

## P2.1 / P2.2 门店预约跟进（2026-09-15）

管理员拥有独立“预约跟进”入口，数字为店休待联系与过期待跟进数量之和；不加入预约审核角标，也不改变顾客已读记录。

- `contact`：所有因店休取消且没有已完成跟进的预约，包括固定店休与单日店休。现有历史店休取消记录也进入队列；首次启用需人工核对既往联系情况并补录，不能把顾客已读推断成已联系。
- `overdue`：仍为 pending 且 `server_now >= scheduled_start_at`、没有已完成跟进的预约。时间到达即可查到，无需 Worker 创建任务；完成跟进不将预约改为确认、拒绝或取消。原过期预约列表保留历史，新的跟进列表只显示尚需处理的事项。
- `retry`（待重试）、`unreachable`（联系方式不可用）均保留待办；下一次联系计划填写在处理说明中，不额外设自动提醒时间。
- `contacted`（已联系）仅用于店休联系，表示门店实际完成联系；`resolved`（已结束跟进）适用于两类事项。结束时必须填写处理结果或无法继续联系的原因；不能用“查看”完成任务。
- 所有写入必须有 1–500 字去除首尾空白的说明；记录处理人、时间与递增版本。只追加、不覆盖；完成为终态，本期不支持修改历史或重新打开。
- 多管理员共享处理结果。预约行锁串行检查业务条件，锁后读取跟进最新版本；expected_revision 不匹配返回 40972。相同 request_key、原版本、结果、说明、处理人重放不重复写入；同键不同内容冲突。
- GET 汇总、分页队列、详情和历史不写数据。列表按预约开始时间、ID 稳定排序，历史按版本倒序分页；完成后的记录仍可查询。
- 仅 ADMIN/SUPER_ADMIN 可读写；顾客不获取门店内部说明。停用身份沿用原鉴权限制。与顾客结果事件、电话拨号、微信投递分别管理；点击拨号不是已联系。
- 只追加记录保存到 `reservation_followups`；不做初始任务回填。保留跟进历史，不随待办消除删除；关联预约、管理员使用 RESTRICT，未来匿名化/保留期限需单独评审。
