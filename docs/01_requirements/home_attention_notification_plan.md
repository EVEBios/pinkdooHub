## 1. 产品目标与设计结论

让下一位需要处理或查看结果的人，在进入小程序首页时就知道发生了什么，并能直接进入对应记录完成下一步。

核心例子：顾客提交一条预约，管理员首页“预约审核”出现红色数字 `1`；管理员确认或拒绝后，该审核待办消失，顾客首页“我的预约”出现红色数字 `1`；顾客打开并成功看到这一条预约的最新结果后，数字消失。两条不同预约计 `2`。

采用三个互相独立的概念：

| 概念 | 表达的事实 | 消除条件 |
|---|---|---|
| 待办 | 当前有一件仍需本方处理的业务 | 业务成功处理或不再符合处理条件；查看页面不能消除 |
| 未读结果 / 新变更 | 对方或系统已经完成某项变更，本方尚未看到 | 本方成功看到对应版本的结果并确认已读；以后再变更可重新提醒 |
| 微信投递 | 尝试在小程序外触达接收者 | 按独立投递状态管理；发送成功不代表站内已读 |

“等待别人处理”“体验进行中”等正常进度用普通状态文案和倒计时表达，不持续制造红色未读提醒。提醒不增加预约、订单或资金状态，也不要求顾客再次同意管理员的处理结果。

## 3. 全项目提醒矩阵

以下“首版”为完整站内目标；当前进度以上方状态及第 9 节为准，矩阵不代表所有候选需求均要实施。P1 为站内闭环，P2 为可选运营增强，W 为备案后单独核验的微信阶段。

| 场景 | 管理员首页 / 管理页面 | 顾客首页 / 顾客页面 | 建议阶段与边界 |
|---|---|---|---|
| 新预约待确认 | 预约审核待办 +1，按预约计数 | 显示等待门店，不生成自己提交的未读结果 | P1 |
| 预约确认 / 无空位拒绝 | 原审核待办消除 | 我的预约新结果 +1，显示真实原因和下一步 | P1 |
| 顾客取消待确认预约 | 原审核待办消除；预约列表保留历史 | 当前操作成功反馈，不给自己再制造一条未读 | P1；未受理取消默认不额外制造管理员红点 |
| 顾客取消已确认预约 | 预约入口出现“已确认预约取消”的新变更 | 当前操作成功反馈 | P1；提醒门店重新安排，任一管理员知悉后共享消除 |
| 自定义 / 固定店休取消预约 | 原审核待办消除；操作结果列出影响与当前联系方式 | 每条受影响预约产生店休取消结果 | P1；电话仍按 N1 人工联系，结构化待联系队列排 P2 |
| 预约到开始时间仍未受理 | 不再算可审核；列表单独显示“已过时未处理”数量和筛选 | 显示“预约时间已到，尚未获门店确认，请联系门店”时间提示 | P1 展示派生提示，不新增 expired 状态；异常跟进队列 P2 |
| 普通订单待付款 | “订单处理”显示待付款待办，含线下核实入口，不声称用户已经支付 | “待支付”待办 +1，可付款或取消 | P1；首页主计数排除已归入待付款桌台的同一订单 |
| 有效待付款桌台 | “桌台工作台”待付款 +1，按会话计，不按 Timer 计 | 一件待支付事项，可从首页回到本次桌台 | P1；默认不增加“我已线下付款”按钮，见 §5.2 |
| 管理员人工确认收款 | 原待付款待办消除，订单进入履约队列 | 一件“已确认收款”结果，有桌台则同时说明开始计时 | P1；无桌台普通订单也覆盖 |
| 顾客自己余额付款 | 原待付款事项消除，门店出现履约待办 | 成功页面反馈；结果落库，成功看到后已读，离开/断网未看到则保留提醒 | P1；避免假定响应已被用户看到 |
| 管理员代客钱包下单 | 本次操作反馈，新订单进入履约队列 | 一件“门店代下单并扣款”结果，可查订单与资金记录 | P1；不再重复一件普通扣款通知 |
| 已支付待履约 / 完成 | 合法可完成的订单保持待履约；服务结束后待收尾优先显示；完成后消除 | 完成时一件订单结果 | P1；不能一律把 active 计时订单标为“已到点待结束” |
| 顾客取消普通待付款订单 | 原待付款待办消除；关联待付款桌台也释放 | 操作成功反馈 | P1；不额外推送普通取消消息，减少双向回执 |
| 桌台付款超时 | 桌台待付款消除；订单仍待付款，回到普通订单待付款队列 | 一件占台超时结果，提示重扫或处理原订单 | P1；不自动取消订单或恢复库存 |
| 管理员提前释放桌台 | 当前桌台事项消除；原订单独立处理 | 一件提前结束结果，说明付款/退款/订单是否仍待处理 | P1；不把释放写成退款成功 |
| 计时自然到期 | 桌台释放；原 paid 订单继续待履约收尾 | 普通计时结束状态，默认不加持久未读 | P1；临近到点和离开页面主动提醒排 P2/W |
| 退款成功 | 本次操作反馈；排除不能再完成的已退款订单 | 一件退款结果；钱包显示退回余额，人工显示门店登记线下退款 | P1；订单、钱包、桌台关闭合并为退款事项 |
| 管理员余额调账 | 操作反馈 | 每笔调整一件资金结果，显示正负金额与安全的原因说明 | P1；单独纠错是新流水，不能覆盖原调整 |
| 直接开台 / 结束 | 管理桌台状态与操作反馈 | 无接收者，不产生顾客事项 | P1 边界；未来绑定顾客须另行设计 |
| 店休恢复营业 | 显示营业日历变化 | 不通知历史取消预约“恢复成功” | 不纳入；历史预约不会复活 |
| 真实充值/微信付款/退款处理中、失败、最终结果 | 可操作的异常/对账项进入运营队列 | 可信服务端结果及需要本人补充操作的事项 | 后续支付项目 + W；当前关闭路径零业务事件 |
| 顾客申请退款、改期审核、加时/换桌申请 | 相应审批待办 | 审批结果 | 业务本身未实现，不能只加提醒先行开放 |
| 门店用豆库存 | 无主动提醒；管理员在库存页按状态和颜色分组筛选 | 无 | P2.4 已实现独立库存管理；库存不足筛选为已盘点且不大于 1 包，不做红点/红边，见 [门店用豆库存规划](store_bead_stock_plan.md) |
| 商品发布/下架/改价、图片、颜色、库存日常调整 | 操作者成功反馈及原有审计 | 无普遍通知 | 当前没有发布审批或补货订阅；历史订单/预约快照不受当前商品变更影响 |
| 注册、资料修改、权限管理、禁用/注销 | 原有操作/安全反馈 | 本人反馈或认证错误 | 当前无注册/注销审核；被禁用用户不能登录，不能依赖首页红点通知账号禁用 |
| Worker 故障、资金对账差异、安全异常 | 运维告警；有明确业务处理动作后才能加入管理事项 | 不直接展示内部错误 | 独立运维范围，不把所有日志转成首页通知 |

## 4. 首页与列表如何呈现

### 4.1 ADMIN+ 工作台

保留现有结构、品牌和真实入口：

- “预约审核”右侧显示红色数字；副文案明确“待审核 2 · 取消变更 1”。入口数字为两类事项按预约去重后的数量，不能把未读与待审核当成同一状态。
- “订单处理”显示普通待付款与待履约事项的去重数，并在副文案分项；“已退款但仍 paid”的订单不算待履约。
- “桌台工作台”显示有效待付款会话数量；活动桌数、体验剩余时间继续用普通状态展示。
- “用户与权限”不把每笔正常调账/退款再算作管理员待办；当前没有独立退款审批入口。
- “今日处理”分组名称与副文案应调整为“待处理”等准确表述，或明确标明“含未来预约”；首页审核不能只统计今天而漏掉未来待确认预约。

同一个已绑定桌台的待付款订单，首页主归属“桌台工作台”，不同时增加“订单处理”的主角标；完整订单列表仍能查到它，并注明桌台处理中。订单付款后转入订单履约队列，因此一次收款可能让桌台角标减一、订单角标加一，这是新的下一步，不是旧提醒未清除。

点击角标与点击其所属入口为同一动作，优先打开“待处理/新变更”视图。审核按开始时间从近到远排序，未读变更按最新事件排序；完整历史维持既有稳定排序。初始进入提醒视图需要显式过滤参数或独立列表能力，不静默修改现有全部列表的排序契约。

### 4.2 顾客首页与根导航

用户当前首页是商城。新增仅登录普通顾客可见的紧凑提醒区，位于商城标题/扫码入口附近，只有存在事项时显示对应行：

- “我的预约 · 1 个新结果”。
- “我的订单 · 1 笔待支付 / 1 个新结果”。
- “当前桌台 · 待付款 / 已确认收款”，跳转精确会话；进行中的倒计时用普通展示。
- “资金明细 · 1 笔余额变动”。

保留“商城 / 预约 / 购物车 / 会员中心”四个根 Tab，不另建消息 Tab。预约 Tab 同步预约结果角标；会员中心入口可汇总订单/资金事项，会员页内部再按订单、待支付、资金明细分项。购物车数量独立，不加入业务提醒总数。

同一事项在多个导航位置显示属于同一提醒的入口镜像，不能再次累计；会员中心汇总按事项并集计算。首版不再额外展示一个容易重复相加的全站总数。未登录不显示私人数量，管理员不请求顾客汇总。

### 4.3 数字、可读性与反馈

- `0` 不显示；`1–99` 显示真实数字；超过显示 `99+`，列表仍给真实总数。
- 单位为业务事项：两条独立预约计 2；一个开台会话多个计时器仍计 1；一笔退款附带余额与库存变化仍计 1。
- 红底白字，单数字圆形、双数字/`99+` 自适应圆角宽度；不闪烁、不遮挡入口名称，不让极小角标成为单独点击目标。
- 辅助阅读文案说明“预约审核，2 件待处理”等，不能只靠红色表达意义；保留现有触控尺寸与减少动态效果约定。
- 加载中不先闪出 `0`；首次读取失败显示提醒暂不可用，有旧数据时保留旧值并说明更新时间/刷新失败；失败不能假装没有待办。
- 提醒不可用不得阻断进入原业务列表、详情或已有合法操作。

## 5. 两条核心流程与资金交接

### 5.1 预约闭环

1. 顾客创建成功：服务端真实生成一条预约；管理员可审核数增加，顾客看到“等待门店确认”。同一次点击仍遵循现有前端防重规则；两个真实成功创建的预约是两件事项。
2. 管理员打开列表/详情：待办保留。确认/拒绝事务成功后，审核待办消除，同事务记录顾客可见结果。
3. 顾客回首页看到结果角标；打开对应详情，最新状态、原因、预约时间和建议操作成功展示后，只确认已展示版本为已读。
4. 管理员确认后又遇店休：顾客该预约仍只计一件待查看事项，展示最新店休取消，同时保留确认历史。先前的确认消息不能覆盖取消结果。
5. 顾客取消已确认预约：门店新增一件取消变更，任一 ADMIN+ 在该变更处点击“已知悉”后共享消除，并记录知悉人/时间。仅打开首页或列表不消除。
6. 临界时间以服务端为准：`now >= scheduled_start_at` 不计可审核；“已过时未处理”在列表保留独立提示，不假装已拒绝、已取消或已服务。若需要长期异常跟进，P2 增加明确的处理记录，而非修改预约状态冒充已处理。

店休仍须人工联系受影响顾客。角标已读不能证明门店已经电话联系；管理员点击设置店休成功也不能证明顾客已获知。P2 的待联系队列需要明确联系成功、待重试、联系方式不可用等独立处理结果，与本次结果已读分开。

### 5.2 开台与确认付款

已确认产品决策（2026-09-14）：首版提醒全部仍有效的待付款桌台，不增加顾客操作步骤。

1. 顾客绑定订单开台：桌台形成待付款会话，管理员桌台入口 +1，顾客首页显示该会话待支付；只是等待付款，不声称已线下到账。
2. 顾客使用余额：可信付款成功后自动激活计时，无需管理员再批准付款。顾客成功看到结果后已读；管理员的待付款转为订单履约待办。
3. 顾客线下付款：店员核实整单实际到账，再通过现有“确认已收款并计时”操作处理，绑定精确会话；页面保留桌号、订单、顾客、应收与时长核对。
4. 同一事务完成付款/订单/桌台激活和一件用户结果；首页可以显示“门店已确认收款，T03 开始计时”。顾客停留在桌台页并看到结果后同步已读，离开页面则保留角标。
5. 成功处理桌台不等于完成订单。订单仍进入待履约队列；服务完成才消除该待办。
6. 超时只释放会话，原订单仍待付款；顾客看到“占台已超时，订单尚未付款”，可重扫或处理订单。不要因为“当前会话为空”丢失超时结果。
7. 原会话被释放后又创建新会话，旧提醒必须打开旧会话结果，不能跳到当前新会话并顺手标记旧事件已读。现有“当前会话/订单最新会话”接口不足以保证该语义，P1 需设计 owner-only 的精确历史会话查询或等价结果详情能力。

备选扩展：如果以后希望将“普通等待付款”和“顾客已请求核实收款”分开，可增加“我已线下付款，请店员核实”按钮。它只登记核实请求，不能创建 Payment、启动计时或证明到账；还需设计重复点击、撤回、超时、钱包付款并发和核实未到账的处理闭环，故不作为首版依赖。

### 5.3 资金结果与履约

- 管理员代客下单：合并显示“门店代下单并从余额扣款”，详情关联原订单/资金事实。不能把内部两条审计、库存扣减、Payment 和钱包流水转换成多条用户提醒。
- 余额调整：按不可变调账流水计数，准确展示变化方向、金额与顾客可见原因；通知只引用必要事实，不复制内部备注或完整个人信息。
- 钱包退款：一件“已退回余额”；人工退款：一件“门店已登记线下退款”，不声称系统验证了线下资金送达。
- 已退款订单仍可能为 `paid/completed`；管理员待履约必须排除 `pending/succeeded` Refund 等现有完成规则明确禁止的情况，不能只统计 Order.status。
- 有 active 桌台的 paid 订单标为“服务中”，仍属于履约事项但不催促立即结束；时间到期后变为“待收尾”。没有桌台的 paid 订单按原人工履约流程处理。
- 付款结果未知：保留原操作意图，读取权威订单/资金/会话，不根据首页角标重放扣款。失败事务不产生成功结果提醒。

## 6. 计数、已读、多人协作与失效规则

### 6.1 计数规则

待办由当前业务事实派生；未读结果由持久化结果及阅读记录决定。每个模块分别返回待办数、未读事项数和去重展示数。

建议事项键：预约使用预约 ID，订单及其支付/退款/代客扣款使用订单 ID，独立调账使用流水 ID，独立桌台超时/人工释放使用精确会话号。同一结果关联多个资源仍指定一个主事项；付款、退款或订单完成导致的桌台变化作为该事项的附属结果，不另造一件桌台提醒。无付款/退款/完成原因的超时与管理员释放才使用独立会话事项。

同一事项既有未读结果又有待办，入口只计一件，详情同时说明两者。阅读结果不会消除仍需付款的待办。不同的调账流水不得因属于同一钱包而合并，以免漏看不同资金动作。

### 6.2 阅读规则

- 打开首页、预加载详情、进入列表、拉取接口、微信发送成功都不是已读。
- 默认在详情前台可见且对应结果内容成功展示后确认已读；停留详情时收到的新版本也遵循同一规则。
- 已读写入幂等，绑定服务器确认的接收者、事项和已展示事件 ID 集合；服务端验证这些事件确实可见，客户端不能上报任意用户或“最新全部”。
- 按明确事件集合确认，而非拿数据库自增 ID/客户端时间充当全局已读水位；较晚提交的并发事件不能被误清。
- 同一事项聚合展示最新状态时，返回覆盖的可见事件集合/服务器阅读凭据。重要的付款、退款、调账摘要也必须展示，才能同时确认这些结果；不能只显示“已完成”就把未展示的扣款明细全部设为已读。
- 后台已读成功后以服务器结果更新所有镜像角标；失败保留/恢复未读，允许重试。多个设备按同一账号共享用户阅读结果。
- 首版不提供“全部已读”，避免误清未加载分页和并发新结果；以后添加时必须限定用户实际选择的快照范围，且不能完成待办。

### 6.3 管理员共享与权限

- 审核、收款和履约是门店共享工作队列，ADMIN 与 SUPER_ADMIN 看同一范围；A 处理成功后 B 下次刷新看到待办消除。首版不做抢单/指派。
- 双管理员同时操作依赖既有行锁、状态校验和资金唯一结算；失败方刷新并提示已被处理，不再次生成结果。
- “顾客取消已确认预约”等门店知悉事项采用门店共享知悉记录；A 明确知悉后 B 同步消除，不要求每位管理员逐个阅读。
- 顾客结果仅 owner 可读取/已读；角色降级、禁用、注销或登出后清除本机缓存与轮询，服务端重验现有权限，不依赖前端隐藏。
- 被禁用者可能收到合法退款/调账的站内结果记录，但现有认证规则不因此放宽；需要通知时仍走门店既有人工流程。删除账号的记录关联和展示匿名化要随生命周期设计，不能新增可登录能力。
- 无可执行权限或能力被开关关闭的项目，不虚报“可立即处理”；说明当前能力不可用并提供已有可用路径，不丢弃业务事实。

### 6.4 初次上线与保留

- 生效时，真实仍有效的存量待办直接计入，包括未来待审核预约和存量待付款订单，不要求它们都是新创建的。
- 历史已完成结果不默认补成未读，防止上线瞬间出现大量旧通知。以明确的启用边界区分新事件，并验证发布切换窗口无漏记/重记。
- 待办不因为“创建满 N 天”或用户点过就消失。订单当前没有自动取消，不能借提醒系统擅自增加过期取消或释放库存。
- 结果未读首版不静默按天清除；已读索引/事件的保留、匿名化和归档时长在实现前冻结，不与订单、账本、审计的保留周期混为一谈。

## 7. 建议实现边界（设计草案，非现行契约）

### 7.1 最小持久化与事务

建议采用“查询业务待办 + 持久化结果事件/接收状态”，不为每种业务复制一套待办状态机，也不先建设通用消息平台。

| 逻辑对象 | 最小职责 |
|---|---|
| 结果事件 | 唯一事件键、事件类型/版本、主事项及必要关联、发生时间、最小安全结果数据 |
| 接收状态 | 接收目标（用户或门店共享）、事件关联、已读/知悉时间，门店知悉操作者；唯一接收者+事件约束 |
| 汇总读模型 | 经授权的当前待办、未读事项并集、分类与数量；可从 Repository 聚合，不把前端缓存当权威 |

物理表名、外键/索引、归档和 API 字段在实现前设计评审后冻结；此处不预写正式 SQL、迁移或错误码。

原业务 Service 持有事务，通过提醒 Repository 写结果与接收记录，不调用另一普通业务 Service。事件随业务、资金、库存和原有审计一起提交/回滚；读取和已读独立走自己的 Service。AuditLog 保持审计用途，不承担用户消息收件箱，也不让客户端查询内部审计拼装结果。

幂等键来自稳定业务事实/事件类型与版本，不使用每次请求随机新值。重复收款确认、资金幂等重放、后台重复收敛、批量店休重放均不能生成重复结果。发生独立新变化时产生新事件，不能用“每个预约永远一条”吞掉确认后的取消。

事件写入的锁在既有业务锁序之后；已读只锁接收状态，禁止反向锁 User/Order/Session。跨预约批量取消要批量写事件/接收状态，不能循环独立事务。系统时间收敛路径与人工释放路径都要覆盖，尤其精确会话首次关闭事实只能记一次。

首版原子事件写失败则整个本地业务事务失败，避免成功却永久丢结果；HTTP 提醒查询失败不阻断其他业务页面。未来外部付款回调不能通过数据库回滚撤销外部付款，需由支付项目的可信回调/查单重试机制补齐本地事务，这与微信消息投递失败不回滚业务是两个边界。

### 7.2 接口能力

需设计而非现在新增的能力包括：

1. 顾客提醒汇总与 ADMIN+ 工作台汇总，分角色鉴权；返回 `server_now`、模块细分计数、去重数与能力提示，不返回收件人隐私或金额总览。
2. 按模块查看当前待办/未读结果的分页列表，与汇总复用同一筛选和去重语义；读取状态在一次一致性快照内计算，并注明服务端时间。跨请求出现变化时允许刷新纠正，不伪称永远同步。
3. 当前顾客结果的幂等已读确认，以及 ADMIN+ 共享变更的明确知悉；不能用前端任意事件 ID 更新其他接收者。
4. 精确历史会话、资金结果的安全落点；纯流水列表无法定位旧调账时，提供按流水定位/详情能力，不能跳列表首屏就视为已读。

沿用统一成功信封、严格 Out Schema、稳定分页、角色和 owner 权限；新 API/错误/生成类型在实施时同步权威文档和 OpenAPI。汇总不能由客户端并发拉全量预约、订单和钱包流水计算；Repository 使用聚合/批量查询和合适索引，防止首页 N+1。

### 7.3 刷新与前端生命周期

- 登录完成、首页 `onShow`、回到前台、手动刷新，以及处理成功/已读成功后立即重读相关汇总。
- 建议管理员首页前台可见时约 10 秒刷新，顾客约 30 秒刷新；以实现阶段负载验收调整，不承诺小程序关闭后仍轮询。
- 桌台现有更快刷新节奏复用统一数据失效/刷新协调，保持每个页面/会话只有一个归属明确的定时器；不再叠加平行轮询。
- 过期预约和付款会话用同一个服务端时间判断；跨时间边界及时重读，不能等到后台任务跑到才纠正计数。
- 前台切后台、页面卸载、身份变更和登出时停止任务；失败退避，重回前台立即校准。旧账号/旧请求的迟到响应不得覆盖新账号数据。
- 微信自定义底栏与其他端的原生底栏分别适配；不能直接假定一套角标 API 适用于所有端，仍遵循当前平台发布范围。
- 首版无需 WebSocket、独立消息队列或常驻通知 Worker；站内未读必须由数据库持久化，不能只保存本机“最后进入时间”。

## 8. 微信通知：备案后的独立阶段

按本次产品安排，先做站内方案，微信实际接入放在小程序备案通过后再推进。备案通过是否足以使用某能力，必须以目标账号后台和届时官方规则核验；本次没有访问账号后台，也未能读取下列官方页面，不宣称已确认模板权限、订阅次数、长期订阅资格或当前准入条件：

- [微信小程序订阅消息能力](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/subscribe-message.html)。
- [wx.requestSubscribeMessage](https://developers.weixin.qq.com/miniprogram/dev/api/open-api/subscribe-message/wx.requestSubscribeMessage.html)。
- [服务端发送接口](https://developers.weixin.qq.com/miniprogram/dev/OpenApiDoc/mp-message-management/subscribe-message/sendMessage.html)。

### 8.1 与原 N2 规划的关系

[原 N2 店休通知规划](reservation_wechat_notification_plan.md) 只涵盖 `reservation_cancelled_store_closed`，明确不含确认/拒绝、顾客取消和支付消息。本规划扩大的是未来候选事件清单，不等于扩展已批准的 N2 范围；站内阶段也不依赖 N2。未来实施扩展前应同步 N2 的范围、授权场景、模板映射、隐私与验收，保留原决策历史。

推荐外部通知优先级：

1. 顾客预约确认/拒绝、店休取消：用户不在店，最容易错过结果。
2. 顾客退款结果、管理员代客扣款/余额变动：需要核对对应消息模板和授权场景，不能用预约模板发送资金消息。
3. 开台付款确认、体验到时：站内自动刷新先满足现场场景，再根据真实需求决定外部通知。
4. 管理员新预约/顾客取消：独立核验员工接收方式和可用消息能力，不能默认普通顾客订阅模板能用于工作人员，也不承诺永久后台推送。

### 8.2 必须保留的设计边界

- 顾客通过明确的业务操作自愿选择订阅；拒绝、不支持、调用失败不影响预约或付款业务。具体触发限制和次数以实施时核验为准。
- “确认结果”和“后续店休取消”是不同事件；不能假定一次授权足够发送全部变化，也不能消耗为店休保留的机会去发确认。先确定模板与机会分配规则。
- 站内结果事件可作为未来投递来源；另建持久 Outbox 和投递状态/租约/重试/抑制规则，不复用 read_at 表示已投递。
- 微信请求在事务提交后异步执行，失败/延迟不改变已提交预约、订单或退款；超时结果未知要与明确失败区分，不能保证绝对不重复或一定送达。
- 投递前重查最新业务：已确认又被店休取消时，抑制仍未发送的过时确认，保证消息不会把顾客引导到失效状态；原业务事件历史保留。
- 不以站内已读直接等价为“禁止微信发送”；可否抑制已读结果需按事件类型显式定策略，特别是预约取消。
- 当前 ExternalIdentity 只保存不可逆 HMAC，不能用于消息投递。实际接入需要经评审的独立加密收件地址、重新取得微信身份、订阅登记与注销/解绑处理，遵循 N2 的身份和隐私边界；本期不增加 OpenID 存储。
- 管理页面可以显示投递摘要和人工联系兜底，但“微信已接受请求”“顾客站内已读”“门店已联系”必须分列，不能混称已通知成功。
- 微信端通知点击仍需登录、身份恢复、owner 校验后打开精确结果；不得携带金额、手机号或任意页面/收件人到不可信参数。

正式模板、合法页面、iOS/Android 真机、消息拒绝/失败、密钥、监控、人工兜底和发布证据完成后再启用，不把本次规划当作配置或发布授权。

P1.1 可以独立验收，但若后续只交付预约，应准确称为“预约提醒已完成”，不能把整个站内提醒项目标为完成。

关键验收用例：

1. 两个顾客各提交一条预约，管理员显示 2；查看不减，接受一条后减为 1；仅对应顾客有结果 1。
2. 拒绝、店休取消与确认文案各自准确；同一预约连续变化只计一个事项，最新状态不可被旧响应覆盖。
3. 顾客已确认预约取消被任一 ADMIN+ 明确知悉后，共享变更消除；其他可审核预约数量不受影响。
4. 到开始时间的 pending 不再进入可审核队列；到付款截止边界遵守现有可信付款时间规则，首页与业务操作不会使用不同时间口径。
5. 一个含多个 Experience Timer 的桌台只计 1；人工与钱包付款竞争只有一次结算、一个合并结果，不重复计时。
6. 付款成功响应丢失仍可从首页找回结果；已在前台看到并成功标记后，首页不再要求重复阅读。
7. 付款/退款/完成引起桌台关闭不另加重复角标；独立超时/管理员释放按会话定位，旧事件不会误开新会话。
8. 钱包退款与人工退款文案、订单主状态和待履约排除正确；管理员代客订单只产生一件扣款结果。
9. 读旧事件与新事件并发、已读失败重试、慢事务晚提交、列表分页未加载时，都不能吞掉未展示结果。
10. 初次上线存量有效待办可见，历史结果不全量亮红；没有数据/正在加载/获取失败/99+ 各自准确。
11. USER/ADMIN/SUPER_ADMIN、他人记录、disabled/deleted、账号切换、同账号多设备覆盖完整；direct 会话不会给任意用户发消息。
12. 多管理员和事务回滚/重试、重复店休/收敛都不重发结果；真实 MySQL 下检查批量写与汇总/未读查询计划、锁序和死锁重试。
13. 新增轮询与已读重试在退出页面/后台/登出时清理，不增加多份后台定时器；弱网重连能恢复真实数字。

实施验证顺序：先定向后端业务/HTTP/事务和前端交互测试，再做跨模块回归、项目格式/静态检查及风险相应的完整 `pytest tests/ -q`；数据库并发与索引需要隔离 MySQL 证据，不能由 SQLite 代替。本轮未实现，因此不运行或宣称通过这些未来测试。
