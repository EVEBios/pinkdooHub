## 2. 目标与范围

### 2.1 目标

1. 为门店固定创建 30 个桌台二维码，对应 `T01`–`T30`。
2. 顾客扫码后可将本人一笔符合条件的待支付订单绑定到该桌台，形成 15 分钟待支付占台。
3. 订单成功付款后，以可信付款成功时间为统一起点，按 Experience 商品的订单快照生成计时器。
4. 相同时长的 Experience 项合并成一个计时器；不同时长分别计时，但都归属于同一个桌台会话。
5. 每个不同的体验时长都额外增加 10 分钟缓冲时间。
6. 最长计时器结束后自动释放桌台，不自动完成订单。
7. Kit 可以与 Experience 同单购买，但 Kit 不参与开台资格以外的计时计算，也不改变现有库存语义。
8. 首阶段只用于内部验收，支持现有钱包支付和管理员人工结算；真实微信支付另行立项。

### 2.2 首版明确不做

- 不做人数、座位数或桌台容量模型。
- 不把预约自动绑定到桌台、订单或计时会话。
- 不支持纯 Kit 订单开台。
- 不因 `quantity > 1` 延长或复制计时器。
- 不因计时结束自动将订单改为 `COMPLETED`。
- 不在数据库中每秒更新剩余时间。
- 不依赖 Redis 定时器保证正确性。
- 不在本阶段接入真实微信支付、退款回调或商户平台能力。
- 不在公开 API 中创建、轮换或批量下载二维码物料。
- 不承诺转发后的二维码只能由店内顾客使用；首版静态码是桌台定位码，不是秘密凭证。

## 3. 领域语言

| 名称 | 定义 |
|------|------|
| Store Table | 门店内固定桌台，首版精确为 `T01`–`T30` |
| QR Token | 二维码携带的不透明随机桌台定位符；可公开，不等同于鉴权凭据 |
| Table Session | 一次“用户 + 订单 + 桌台”的开台生命周期，可处于待支付、计时中或已关闭 |
| Occupancy | 当前占台记录；只表达桌台此刻被哪个未关闭会话占用，不保存历史 |
| Timer | 根据一个不同的 Experience 时长快照生成的计时记录 |
| Payment Window | 从成功占台起计算的 15 分钟待支付窗口 |
| Service End | `started_at + duration_minutes`，体验时长结束点 |
| Grace End | `service_ends_at + 10 分钟`，缓冲结束点 |
| Table Release At | 会话内所有计时器 `grace_ends_at` 的最大值 |
| Trusted Payment Time | 已落库成功付款记录的 `Payment.succeeded_at`；不得使用客户端时间 |

## 4. 核心业务规则

### 4.1 固定桌台与二维码

1. 首版必须且只能存在 30 个桌台，编号精确为 `T01`–`T30`；初始化时全部启用，之后允许管理员逐桌停用。
2. 每个桌台有一个唯一、不可预测、大小写敏感的 32 位纯字母数字 `qr_token`。
3. 当前内部验收二维码携带固定前缀与 `qr_token`：`PINKDOOHUB_TABLE:v1:<qr_token>`，不携带数据库自增 ID、订单 ID、用户 ID、价格、时长或付款信息。客户端通过 `Taro.scanCode` 解析后进入固定桌台页。
4. `qr_token` 是公开定位符，不是授权凭据。扫码解析可公开访问；占台、查询本人会话和后续付款仍要求登录。
5. 桌台可以被管理员停用。停用只阻止新会话，不中断已经开始的有效会话；如需提前释放，必须执行显式释放操作。
6. 当前普通二维码只是备案前内部验收占位物料；必须标记环境并由受控运维任务生成。切换为微信官方小程序码时，必须先明确目标 AppID、页面路径与版本，保持 Token/桌号映射不变并重新完成真机验收。占位物料不得冒充正式小程序码。

### 4.2 开台资格

创建桌台会话时必须同时满足：

1. 当前用户是状态正常的普通 `USER`。
2. 二维码能解析到存在且已启用的桌台。
3. 订单属于当前用户。
4. 订单仍为 `PENDING`，且没有成功付款或有效结算事实。
5. 订单至少包含一个 Experience Item。
6. 每个参与计时的 Experience Item 都有有效的 `option_duration_minutes` 订单快照。
7. 当前用户没有其他未关闭桌台会话。
8. 当前订单没有其他未关闭桌台会话。
9. 当前桌台没有其他 Occupancy。

纯 Kit 订单不满足第 5 条，不能开台。混合订单可以开台，其中 Kit Item 被忽略，不进入计时器。

### 4.3 扫码后的订单选择

1. 顾客扫码后可选择本人已有的符合条件的 Pending 订单。
2. 顾客也可以从桌台入口进入商品详情和购物车；本次选桌按账号保留。统一订单确认页在同一次提交中创建订单并占台，成功后直接进入订单付款，无需返回扫码页。
3. 创建新订单仍完全遵循 Order 与 Inventory 的既有契约；二维码功能不得绕过商品、Option、库存、价格快照或订单创建校验。
4. 可选订单列表只展示本人符合开台资格的 Pending 订单，并提供用于决策的 Experience 时长分组摘要。
5. Kit 信息可作为订单摘要展示，但不得出现在计时器或桌台释放时间计算中。

### 4.4 待支付占台

1. 成功创建会话后立即进入 `AWAITING_PAYMENT`，并写入当前 Occupancy。
2. `payment_deadline_at = claimed_at + 15 分钟`。
3. 15 分钟内桌台不能被其他用户或其他订单占用。
4. 若可信付款成功时间满足 `succeeded_at <= payment_deadline_at`，允许激活会话；晚于截止点则不得激活。
5. 超过截止点且未形成成功付款事实时，会话关闭、Occupancy 删除，关闭原因为 `PAYMENT_TIMEOUT`；精确等于截止点的可信付款时间仍按第 4 条允许。
6. 超时只释放占用，不取消订单，也不恢复 Kit 库存。曾关联桌台的待付款订单必须重新绑定有效桌台后付款，或取消订单；不得因无当前占用而静默退化为普通付款。
7. 同一订单可以拥有多条历史会话，例如第一次占台超时后再次扫码；但任一时刻最多只能有一条未关闭会话。
8. 会话创建必须支持严格幂等：同一个 Idempotency-Key 与相同规范化请求重放返回原结果；相同 Key 携带不同请求必须冲突。

### 4.5 付款成功与统一起点

1. 首阶段只有现有钱包支付和管理员人工结算能激活桌台会话。
2. 所有计时器的 `started_at` 必须严格等于该订单成功付款记录的 `Payment.succeeded_at`。
3. 客户端上传时间、HTTP 到达时间、任务执行时间、管理员设备时间均不得作为计时起点。
4. 订单付款、Settlement/Payment 写入、Order 转 `PAID`、会话转 `ACTIVE`、计时器写入和 Occupancy 保留必须处于同一个数据库事务。
5. 任一步失败，资金事实、订单状态和桌台状态必须一起回滚，不能出现“已扣款但未计时”或“已计时但未付款”。
6. 付款幂等重放不得重置 `started_at`、延长截止时间或重复创建计时器。
7. 对从未关联桌台会话的普通订单，现有付款行为保持不变。
8. 桌台计时页调用钱包付款时必须携带 `Table-Session-No`，把付款意图绑定到精确 Session；指定 Session 已超时或已被其他原因关闭时资金零写入，顾客须重新扫码。
9. 未携带 `Table-Session-No` 的入口按订单最新 Session 校验：有效待支付 Session 自动关联；已结束/超时 Session 拒绝付款并要求重新选桌；从未关联 Session 的订单按普通订单付款。
10. 管理员人工结算按订单锁后发现的唯一未关闭 Session 自动关联；已超时 Session 不得被静默激活。

桌台计时页和管理桌台页发起的人工结算都应携带 `Table-Session-No` 精确绑定会话。未携带 Header 的现有普通订单/人工结算入口可以继续处理没有未关闭 Session 的订单；曾关联 Session 的待付款订单必须先重新选桌，所有入口均不得绕过这一限制。

### 4.6 多项、数量与计时分组

计时只读取不可变的 Order Item 快照，不读取 Product/Option 当前配置。

处理规则：

1. 过滤全部 Kit Item。
2. 读取所有 Experience Item 的 `option_duration_minutes`。
3. 按分钟数精确分组。
4. 每个不同分钟数生成且只生成一个 Timer。
5. Timer 的 `buffer_minutes` 固定快照为 10。
6. `service_ends_at = started_at + duration_minutes`。
7. `grace_ends_at = service_ends_at + buffer_minutes`。
8. `table_release_at = max(timer.grace_ends_at)`。

`quantity` 只表达购买数量/参与份数，不参与时长运算：

- 1 个 120 分钟 Experience，`quantity = 3`：只生成一个 120+10 分钟 Timer。
- 120 分钟 Experience A 与 120 分钟 Experience B：合并为一个 120+10 分钟 Timer。
- 60 分钟 Experience 与 120 分钟 Experience：生成 60+10 和 120+10 两个 Timer，都从同一个付款成功时间开始。
- 120 分钟 Experience + 任意 Kit：只生成 120+10 分钟 Timer。
- 只有 Kit：不能开台。

同一时长 Timer 的响应摘要可以列出多个 Experience Item 以及各自 `quantity`，但聚合展示不得改变计时规则。

### 4.7 计时阶段与桌台释放

会话为 `ACTIVE` 时，Timer 阶段由服务端当前时间动态推导：

| 条件 | 阶段 |
|------|------|
| `server_now < service_ends_at` | `EXPERIENCE` |
| `service_ends_at <= server_now < grace_ends_at` | `GRACE` |
| `server_now >= grace_ends_at` | `ENDED` |

父 Session 已为 `CLOSED` 时，全部 Timer 无条件显示 `ENDED`。每个 Timer 的实际结束时间从父会话推导为 `min(grace_ends_at, session.closed_at)`；因此短 Timer 自然结束后不会被后续最长 Timer 的关闭时间延长，而管理员提前释放、订单完成或退款会让尚未自然结束的 Timer 立即结束。该实际结束时间只作为响应派生值，不额外写入每条 Timer。

边界规则：

1. 到达 `service_ends_at` 的瞬间进入缓冲阶段。
2. 到达 `grace_ends_at` 的瞬间该 Timer 结束。
3. 到达 `table_release_at` 的瞬间，会话应收敛为 `CLOSED` 并释放 Occupancy。
4. 自动释放不修改 Order；已付款订单继续保持 `PAID`，等待现有管理员完成流程。
5. 查询接口必须返回 `server_now` 和绝对时间戳，客户端只负责展示倒计时，不作为权威状态源。
6. 不进行每秒数据库写入。定时清理任务用于及时收敛，读取、扫码占台、付款、完成和退款入口还必须进行惰性收敛，因此正确性不依赖调度器恰好准时运行。

同一锁内多个关闭条件同时成立时，先按时间边界收敛，再处理人工/订单动作：`now > payment_deadline_at` 优先记为 `PAYMENT_TIMEOUT`；`now >= table_release_at` 优先记为 `TIME_EXPIRED`。付款是唯一例外，使用本次可信 `succeeded_at <= payment_deadline_at` 判定，精确截止点仍可激活。首次持久化的关闭原因和时间不可被后续完成、退款或释放改写。

### 4.8 提前关闭

以下事件关闭整个 Table Session、结束全部 Timer 并删除 Occupancy：

| 事件 | 允许状态 | 关闭原因 | 对订单的影响 |
|------|----------|----------|----------------|
| 待支付超时 | `AWAITING_PAYMENT` | `PAYMENT_TIMEOUT` | 不改订单 |
| Pending 订单取消 | `AWAITING_PAYMENT` | `ORDER_CANCELLED` | 沿用现有取消规则 |
| 管理员完成订单 | `ACTIVE` | `ORDER_COMPLETED` | 订单转 `COMPLETED` |
| 成功全额退款 | `ACTIVE` | `REFUNDED` | 沿用现有退款规则 |
| 管理员显式释放 | `AWAITING_PAYMENT` / `ACTIVE` | `ADMIN_RELEASED` | 不自动改订单 |
| 最长 Timer 到期 | `ACTIVE` | `TIME_EXPIRED` | 不改订单 |

管理员显式释放是应急能力：

- 需要 ADMIN+ 权限、原因、Idempotency-Key 和审计。
- 只释放桌台与计时会话，不自动取消、完成或退款订单。
- 已关闭会话再次释放按严格幂等规则返回原结果或状态冲突，不得改写首次关闭事实。

### 4.9 订单、库存、退款与预约的边界

#### Order

- Table Session 引用订单，不成为 Order 聚合内部 Item。
- 自动到期不完成订单。
- 订单取消与管理员完成必须在原事务中同步关闭关联会话。
- 已关闭会话保留历史，不因订单后续变化删除。

#### Inventory

- Kit 下单时扣减、Pending 取消时恢复、付款/完成不改库存的规则保持不变。
- 待支付桌台超时不是订单取消，因此不得恢复 Kit 库存。
- PAID 订单退款时的 Kit 恢复行为保持现有规则；桌台关闭只是同事务中的附加结果。

#### Payment / Refund

- 桌台激活必须使用可信 `Payment.succeeded_at`。
- 首版不改变钱包金额、流水、Settlement、Payment 或 Refund 的计算规则。
- 全额退款成功时关闭仍未结束的桌台会话；已关闭会话不重开、不改写原关闭时间。

#### Reservation

- Reservation N1 与 Table Session M9 相互独立。
- 预约不预占具体桌台，不自动创建订单，不自动开台。
- 桌台占用不改变预约容量或审核逻辑。

## 5. 状态机

### 5.1 Table Session 状态

```text
                         付款成功（截止时间内）
AWAITING_PAYMENT --------------------------------> ACTIVE
        |                                            |
        | 超时 / 订单取消 / 管理员释放                | 最长计时到期
        |                                            | 订单完成
        |                                            | 全额退款
        |                                            | 管理员释放
        +-----------------------> CLOSED <-----------+
```

状态只允许单向前进：

- `AWAITING_PAYMENT -> ACTIVE`
- `AWAITING_PAYMENT -> CLOSED`
- `ACTIVE -> CLOSED`
- `CLOSED` 为终态

不支持暂停、续时、恢复、换桌或将关闭会话重新激活。未来如需这些能力必须另行冻结契约。

### 5.2 Occupancy 生命周期

- 创建 `AWAITING_PAYMENT` 会话时创建。
- 会话转 `ACTIVE` 时继续保留，不新建第二条。
- 会话转 `CLOSED` 时删除。
- Occupancy 是并发唯一性和快速查询结构，不是审计历史；历史以 Table Session 为准。

## 6. 并发、事务与锁顺序

### 6.1 全局锁顺序

涉及桌台的写事务必须遵守以下顺序中适用的部分：

```text
User
  -> Order
    -> StoreTable
      -> TableSession / TableOccupancy
        -> Settlement / Payment / Refund
          -> WalletAccount
            -> ProductKit / ProductKitColor
```

不适用的锁可以跳过，但不得反向获取。通过 Session ID 或 Table ID 发起的操作可以先无锁解析关联 ID，进入事务后必须回到 `Order -> StoreTable -> Session/Occupancy` 的顺序重新锁定和重检。

### 6.2 创建会话

单一事务内：

1. 锁当前 User。
2. 锁目标 Order 并重检所有资格。
3. 锁目标 StoreTable。
4. 收敛已超时或已到期的相关会话。
5. 检查用户、订单和桌台唯一占用。
6. 创建 Table Session 与 Occupancy。
7. 写人工操作审计。
8. 重载并提交响应。

数据库唯一约束是最后一道并发保护；业务层仍必须锁后重检并返回稳定业务错误。

### 6.3 付款与激活

钱包支付与人工结算继续由各自 Service 拥有事务。它们直接协调 Table Session Repository，不允许业务 Service 互相调用。

同一事务内：

1. 捕获唯一的 UTC `succeeded_at`。
2. 按全局顺序锁 User、Order、StoreTable、Session/Occupancy 及资金对象。
3. 重检付款截止时间和会话状态。
4. 写资金事实并更新订单。
5. 按订单快照生成 Timer。
6. 将 Session 转 `ACTIVE`，保存 `started_at` 与 `table_release_at`。
7. 提交。

### 6.4 竞态结果

- 付款与待支付超时并发：以锁后看到的可信 `succeeded_at` 和 `payment_deadline_at` 决定，最多一个事务成功改变会话。
- 两人同时扫同桌：StoreTable 锁与 Occupancy 唯一约束保证最多一人成功。
- 同一用户同时扫两桌：User 锁和用户未关闭会话检查保证最多一条成功。
- 同一订单同时绑定两桌：Order 锁和订单未关闭会话检查保证最多一条成功。
- 付款与退款/完成并发：沿用 Order 锁串行化，后续操作锁后重检状态。
- 仅 MySQL 1205/1213 可以用全新事务重试完整用例，最多 3 次；其他数据库错误不自动重试。

## 7. 数据与审计原则

1. Table Session 保存状态、关键时间与关闭原因，Timer 保存不可变计时快照。
2. 不保存可由绝对时间稳定推导的每秒剩余秒数。
3. 不额外复制 Kit Item 到 Timer。
4. 不需要 Timer 与 Order Item 的关联表；响应需要的 Item 摘要从不可变订单快照按时长分组读取。
5. Timer 不持久化独立状态或提前结束时间；父 Session 的终态与 `closed_at` 是整组 Timer 停止的唯一权威事实，响应按 `min(grace_ends_at, closed_at)` 派生实际结束时间。
6. 人工开台、人工释放、付款、完成、退款继续写可归属真实操作者的 AuditLog。
7. 自动超时和自动到期不伪造管理员或用户作为操作者；Table Session 的 `closed_at` 和 `close_reason` 是权威事实。
8. 首版不为自动事件引入独立事件表。只有在后续明确需要事件投递、外部审计或复杂重放时再设计 durable outbox/event log。
9. API、日志、二维码 manifest 和物料不得输出 Idempotency-Key、微信密钥、钱包敏感信息或其他用户隐私。
10. `qr_token` 虽然不是鉴权秘密，应用/Audit/反向代理访问日志仍不得无必要记录完整值；使用桌号、内部 ID、request ID 或 Token SHA-256 摘要定位问题。

## 8. 权限与安全

### 8.1 顾客

- 二维码解析可匿名，只返回最小桌台信息和是否可尝试开台。
- 创建会话、可选订单、当前会话和订单关联会话要求登录且仅限 NORMAL USER。
- 用户只能绑定和查看自己的订单、会话及计时器。
- 对他人资源使用现有资源隐藏策略，不泄露所有者或占台者信息。

### 8.2 管理员

- ADMIN+ 可查询桌台与会话、查看必要的订单/用户摘要、执行显式释放。
- 管理接口不得返回完整手机号、Token、Idempotency-Key 或资金内部敏感字段。
- 人工释放必须记录操作者、原因和幂等结果。

### 8.3 静态码滥用控制

- 解析接口按来源 IP 限流；认证后的占台/查询接口再按当前用户与来源 IP 组合限流，并避免暴露占台者信息。
- 创建会话要求认证、严格 Schema、业务限流和幂等键。
- 15 分钟超时限制远程转发二维码后的长期恶意占台。
- 一用户一未关闭会话、一订单一未关闭会话和一桌一 Occupancy 共同限制批量占位。
- 若实际运营仍出现明显滥用，再单独评估店内动态挑战码；首版不预建。

## 9. 运维与配置

### 9.1 功能开关

M9 应新增默认关闭的新占台开关，例如 `TABLE_SESSION_CLAIMS_ENABLED=false`。只有在以下条件全部满足后才可启用：

1. 目标环境已完成 M8，并通过 M9 迁移前只读核验、备份与独立恢复。
2. M9 数据库迁移成功，30 个桌台种子数据核验通过。
3. 小程序目标页面、AppID、目标版本和二维码生成参数已冻结。
4. 钱包支付、人工结算、取消、完成、退款与超时竞态门槛通过。
5. 管理员已具备查看和应急释放能力。

该开关只阻止二维码解析进入开台流程和创建新 Session，不得阻断已经存在 Session 的查询、到期收敛、截止内付款激活、订单取消/完成/退款联动或管理员应急释放。这样可以在紧急暂停新占台时安全排空现有会话，避免功能开关制造永久 Occupancy。

### 9.2 桌台种子数据

- 使用可重复执行的受控命令生成/核验 `T01`–`T30`，支持 dry-run 与 apply。
- 已存在且完全一致时视为幂等重放。
- 缺失、重复、编号越界、Token 冲突或字段不一致时 fail closed，不静默覆盖。
- 生产 `qr_token` 必须使用密码学安全随机源生成；不得使用桌号、递增值或可推测哈希。
- Schema 迁移不负责生成环境专属随机 Token，避免不同环境共享同一生产定位符。

### 9.3 二维码物料

- 调用微信官方小程序码接口的凭据只能来自目标环境 Secret，不进入仓库、日志或物料 manifest。
- 使用“获取不限制的小程序码”时，`scene` 原样等于 32 位 Token，不添加 `t=` 等前缀；`page` 独立传 `pages/table-entry/index`。生成前必须再次核对微信官方 `scene` 长度/字符集与目标版本规则，平台约束变化时先更新契约，不能截断 Token。
- 生成物命名建议为 `T01.png`–`T30.png`，同时生成不含密钥的 manifest：桌号、Token 摘要、页面、AppID 摘要、环境、生成时间、文件 SHA-256。
- 生成后验证 30 个文件数量、PNG 内容、尺寸、哈希和扫码落地参数。
- 正式打印前需做真机扫码验收；照片转发可用属于首版预期行为。

### 9.4 时间与清理

- 全部持久时间使用 UTC，API 使用带时区 ISO 8601；小程序按本地时区展示。
- 定时清理批量分页处理超时/到期候选，避免无限制全表加载。
- 外部调度默认每分钟运行一次 sweep；这只决定后台列表收敛及时性。扫码占台和用户/管理员查询仍在锁内惰性收敛，所以到期后不会因最多一分钟调度延迟继续阻塞新顾客。
- 清理任务按稳定 ID 顺序处理并采用短事务；失败可安全重试。
- 所有用户可见查询和冲突写入口仍进行惰性收敛，避免调度延迟导致已到期桌台永久不可用。

### 9.5 小程序流程与倒计时

固定入口页为 `pages/table-entry/index`，从微信启动参数读取原始 `scene`，只做一次平台规定的解码和严格 32 位字母数字校验，再调用后端解析；页面不得自行从 Token 推导桌号。

顾客流程：

1. 解析桌台，展示明确桌号；未登录先完成现有认证，再回到同一桌台入口。
2. 若本人已有未关闭 Session，直接进入该 Session，不允许重复选桌。
3. 否则展示可开台 Pending 订单；可选择已有订单，或进入现有下单流程后返回。
4. 创建 Session 前显示“桌号 + 订单号 + Experience 时长分组 + 15 分钟付款窗口”的确认页；Kit 只显示为“同单购买、不参与计时”。
5. `AWAITING_PAYMENT` 页面显示绝对截止时间与倒计时，可发起钱包付款或等待店员人工结算。
6. `ACTIVE` 页面按 `duration_minutes ASC` 展示多个 Timer，每组列出相关 Experience 与 quantity；顶部单独显示整桌最晚释放时间。
7. Experience 结束后该组进入 10 分钟缓冲；父 Session 提前关闭或最长 Timer 到期后，页面显示已结束并提供返回订单入口。

倒计时实现规则：

- 首次响应用 `server_now` 计算客户端时钟偏移，绝对服务端时间才是权威。
- 前台 `AWAITING_PAYMENT` 每 5 秒查询 Session，以及时发现钱包/人工付款、管理员释放或超时。
- `ACTIVE` 主要用绝对时间在本地平滑显示，每 30 秒以及页面 `onShow`、网络恢复、进入 service/grace/end 边界时重新查询。
- 小程序进入后台时不尝试保持可信 interval；恢复前台后立即重取。
- 到 0 不能仅在客户端擅自改状态，必须查询服务端；查询失败显示“正在确认”，不得继续显示负数或伪造已释放。
- 多个 Timer 使用稳定 Key，刷新只校正时间和状态，不重启动画、不把短 Timer 合并到最长 Timer。

管理员 30 桌工作台按桌号稳定展示 `available / awaiting_payment / active / disabled` 派生状态；前台默认每 10 秒刷新并在页面恢复、释放、付款、完成和退款后立即重取。页面不得伪造占台统计，所有值来自 Table API。

顾客从“我的桌台”进入的“本次桌台”详情（2026-09-14）：

- 待付款显示付款剩余时间；已付款按每个时长组分别显示体验或缓冲剩余时间、商品数量和绝对截止时间，整桌预计结束取 `table_release_at`。已结束会话保留历史时间，不再倒计时。
- 复用 `server_now` 和响应接收时间校准本地时钟，每秒只更新倒计时组件。沿用此详情页每 5 秒状态查询，并在付款／体验／缓冲截止后核对一次服务端；并发中的查询不叠加。
- 阶段切换以服务端响应为准，到零先显示“正在确认付款状态／缓冲时间／结束状态”，失败可重试且保持零，不显示负数，也不据此宣告桌台已释放。
- 隐藏及卸载清除本地计时、轮询和边界查询；恢复前台立即重取并校准。已关闭停止查询。每秒数字更新不触发结果提醒的读取或已读请求。
- 会员中心保留固定入口，不在入口中运行倒计时；扫码落地页原有刷新规则不变。

## 10. 可观测性

至少记录以下无敏感信息指标：

- 会话创建成功/冲突数量。
- 待支付超时数量。
- 钱包/人工付款激活成功与失败数量。
- 活跃会话与 Occupancy 数量差异。
- 自动到期收敛延迟。
- 管理员显式释放数量。
- 幂等重放和幂等冲突数量。
- 锁等待、死锁重试和最终失败数量。

必须提供只读一致性检查：

- 每个未关闭 Session 精确对应一条 Occupancy。
- 每条 Occupancy 对应一条未关闭 Session，且 table/session 唯一。
- `ACTIVE` Session 至少一个 Timer，`AWAITING_PAYMENT` 没有 Timer。
- Timer 时间公式和 Session `table_release_at` 正确。
- `started_at` 与关联 Payment `succeeded_at` 一致。
- `CLOSED` Session 没有 Occupancy。

检查工具只报告，不自动修复。

## 11. 验收矩阵

### 11.1 正常路径

1. 扫 `T01`，绑定本人含 Experience 的 Pending 订单，进入 15 分钟待支付。
2. 120 分钟订单在截止前钱包支付，生成一个 `120 + 10` Timer。
3. 人工结算与钱包支付使用相同激活规则。
4. 同单两个 120 分钟 Item 只生成一个 Timer。
5. 60 与 120 分钟 Item 生成两个同时开始的 Timer，桌台在 130 分钟释放。
6. Experience `quantity = 3` 不乘时长。
7. 混合 Experience + Kit 只按 Experience 计时。
8. 最长 Timer 到期后桌台释放，订单仍为 `PAID`。
9. 管理员完成或全额退款立即释放未结束桌台。
10. 第一次会话超时后，同一 Pending 订单可重新扫码创建新会话。

### 11.2 拒绝路径

1. 纯 Kit 订单开台。
2. 他人订单、非 Pending 订单、已付款订单开台。
3. Experience Item 缺失时长快照。
4. 桌台已被占用、用户已有未关闭会话、订单已有未关闭会话。
5. 停用桌台开台。
6. 付款成功时间晚于 15 分钟截止点。
7. 相同 Idempotency-Key 携带不同请求。
8. 顾客读取他人会话或管理员字段。

### 11.3 事务与并发

1. 同用户双桌并发最多一个成功。
2. 双用户同桌并发最多一个成功。
3. 同订单双桌并发最多一个成功。
4. 付款与超时在截止边界并发时结果唯一且可解释。
5. 付款过程中任一点故障，资金、订单、会话和 Timer 全部回滚。
6. 取消过程 Kit 恢复失败时，订单取消和桌台关闭全部回滚。
7. 退款过程资金或库存失败时，桌台不得单独关闭。
8. MySQL 1205/1213 只重试完整事务，幂等事实不重复。
9. SQLite 行为测试与真实 MySQL 8 并发门槛均通过，不能以前者替代后者。

### 11.4 二维码与真机

1. 仓库工具能够按需精确生成 30 个普通占位二维码，桌号与 Token 一一对应；生成清单只保存 Token 摘要，二维码 PNG 与清单均为 `0600`。本轮 Gate A 可以先只验收 30 桌和 Token 映射，不要求实际生成物料。
2. 若本轮生成占位二维码，则使用微信开发者工具 `develop` 版本验证进入正确桌台页；未生成时此项明确记为 Deferred。iOS/Android 真机扫码仍是后续发布门槛。
3. 相册识别和转发照片可解析同一桌台。
4. 无效、停用和旧 Token 返回稳定错误，不泄露内部 ID。
5. 后续切换微信官方小程序码前后，Token/桌号映射和旧物料处置符合单独批准的发布方案。

## 13. 已冻结决策与未来变更点

已冻结：

- 30 桌，`T01`–`T30`。
- 15 分钟待支付占台。
- 每个不同 Experience 时长增加 10 分钟缓冲。
- 同时长合并、不同时长分开、全部同时开始。

- 内部验收只用钱包/人工结算；真实微信支付单独立项。
- 静态二维码允许转发，依靠认证、限流、唯一占用和超时控制风险。

未来若要支持换桌、加时、暂停、多人拼桌、预约预分桌、按数量串行计时、动态店内码、部分退款对计时的影响或真实微信支付，必须单独评审并更新需求、API、数据库和迁移契约，不得在实现中隐式扩展。


## 14. 管理桌台运营扩展（M11，2026-09-14）

本节扩展此前“所有会话必须绑定订单与顾客”的 M9 首版边界。代码与迁移不代表目标环境已升级；原有 Gate A No-Go 与受保护 pending 处理规则不变。

### 14.1 30 桌剩余时间

- 待付款桌显示 15 分钟付款窗口剩余时间；活动桌分别显示体验剩余时间、10 分钟缓冲剩余时间。
- 多时长订单的卡片显示最长体验一组及分组数量；详情显示全部分组。释放仍取全部缓冲截止最大值。
- 暂停新开台不隐藏已有会话计时。前端每秒更新显示，列表/管理详情每 10 秒校准，顾客待付款页沿用 5 秒刷新；本地到零不表示已成功释放，需读取服务端结果。

### 14.2 线下收款确认

- ADMIN+ 可从待付款桌卡片或会话详情发起“确认已收款并计时”，先显示桌号、顾客、订单号、整单应收金额和体验时长。
- 使用既有人工结算端点，并必须携带精确的 `Table-Session-No`。确认表示整单全额线下到账；计时起点为本次服务端成功收款时间，不接受补填时间。
- 已超时或已关闭会话不可激活；顾客需重新绑定桌台。重复确认返回现有状态冲突，不创建重复 Payment/Settlement、不重置计时。网络结果未知时先读取原会话确认状态。
- 顾客页面自动同步店员确认结果，并提示已在线下付款者不要重复付款。钱包与人工付款竞态沿用唯一结算和既有锁序。

### 14.3 管理员直接开台

- 不要求顾客账号或系统订单；ADMIN+ 选择已启用的空闲桌、一个体验时长，并可填写最多 200 字备注后立即开始计时。
- 选项来自未删除、online/offline 的 Experience 商品下未删除 Option；按分钟去重、升序排列，相同时长选择最小 Option ID 作为配置来源。draft/已删除商品或 Option 不可选。
- 请求携带 Option ID 与所见分钟数；服务端在 Product→Option 锁内重检类型、状态和分钟数，变更后返回 `42262`，不静默使用新时长。
- `source=direct`；顾客、订单、付款与付款截止均为空，记录开台管理员、配置来源、分钟快照和备注。开始时间取服务端成功创建时间，等于 claimed_at；生成一个所选分钟数 +10 分钟的 Timer，事务内写入唯一桌台 Occupancy。
- 不创建 Order、Payment、Settlement、Wallet 或 Inventory 记录；不计入系统销售收入。平台核销由店员在外部平台完成。
- 同一次幂等身份绑定管理员、桌台、配置、时长和规范化备注；重放返回原会话（即使已结束），不重新开始、不延时。与顾客扫码、其他管理员开台竞争同一个桌台锁与唯一占用。
- 沿用新开台总开关和提前结束的 ADMIN+ 权限、原因、幂等及审计要求。直接会话只允许 active→closed，关闭原因为 time_expired/admin_released，不触发订单完成或退款。
- 本轮不增加加时、改时、换桌、平台核销接入或直接开台顾客绑定。

## P1.2 站内交接提醒

有效待付款会话在管理员首页提醒，计数遵守同一付款截止边界，不增加顾客“我已线下付款”按钮。付款结果与订单合并；独立超时、到期和人工释放按精确会话产生顾客结果，direct 会话无顾客结果。历史结果只打开对应会话，即使已重开也不跳到新会话。权威计数/已读与边界见 [提醒需求 P1.2](attention_module.md)。


### 统一购物结算与选桌（2026-09-14）

- 扫码只选择本次购物桌台，不占位、不计时。商品详情、购物车、确认页共享按账号保存的选择；再次扫码换桌需确认。选桌保存 2 小时，失效后明确提示重新选桌，不能自动变成普通订单。
- 商城确认页可扫码或输入 1–30 号桌，显示规范桌号供用户确认。未选桌是普通购买；纯 Kit 不开台，混合订单只为 Experience 计时。
- 新开台订单复用 `POST /orders`，必须同时提供 `table_no` 和 `table_checkout_key`。Order Service 持有新订单、明细、占台、库存、审计的同一个事务。任一步失败全回滚。
- 幂等请求指纹含账号、桌号、规范化商品项和备注。复用 TableSession 现有 claim key/fingerprint 保存提交身份，已结束的 Session 也可找回原订单；重放不重新占台、不延长付款期限。无需新增字段或迁移。
- 现有待付款体验订单可在详情选择桌台，仍使用现有创建 Session 用例，不创建新订单。当前有效会话不能直接改桌号；已结束后可重新选择。
- 同一用户最多一个未结束会话；有效占台 15 分钟，付款后才启动计时。购物上下文在新订单成功或选择既有订单占台成功后消费，清理必须匹配本次选择，不能删除之后的新选择。
- 客户端在发送开台订单前持久化原请求。网络/超时/响应未知时保留，重新进入确认页显式核对原请求和幂等键，结果未明时不允许换桌或普通下单。恢复订单时保留当前购物车并提示核对，避免重复清理后来加入的商品。
- 已支付普通订单不支持事后补桌台。先购买、日后核销的体验券，以及进行中桌台加购/续时，仍不在本次范围。


## P2.3 管理员桌台到时预警（2026-09-15）

- 用户确认首版提前 **10 分钟**提醒。对 active 会话逐组判断：`service_ends_at - 10分钟 <= now < service_ends_at` 为即将到时，`service_ends_at <= now < grace_ends_at` 为缓冲提醒。单组缓冲结束后不再提醒该组，其他组继续独立判断。
- 同桌任意一组满足即显示到时提醒，红圈按桌去重。直接开台、已暂停新开台但仍使用中的桌台同样纳入；空闲、closed、awaiting_payment 不属于到时预警。
- 管理员首页“桌台工作台”的红圈合并有效待付款桌与到时桌，两类从同一桌台快照计数，防止付款转计时时重复计算。待付款仍沿用 `now <= payment_deadline_at` 的边界；顾客不增加付款申报步骤。
- 桌台页提供“全部桌台／需关注”完整按钮，显示收款与到时桌数；卡片保留最长组总览，并逐组列出临近到时／缓冲提醒，详情突出对应计时组。
- 查看、切换筛选不消除预警；全部计时走完而服务器尚未确认结束时保留“待确认结束”，以重读后的真实关闭／释放为准，不在本地提前宣告空闲。提前结束仍走既有原因、权限和审计流程。
- 不新增已读事件或处理记录，不改订单、支付、自动释放或既有 10 分钟缓冲规则；不新增数据库结构。微信推送另属 W 阶段。
